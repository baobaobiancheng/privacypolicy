
## 修订方案：基于 Markdown 表格的模块化提取

### 一、核心思路

每个提取模块输出一张或多张 Markdown 表格，**每张表都自带原文依据列**。表格是二维的，眼睛扫起来比嵌套 JSON 快得多，而且可以直接在 Markdown 预览/编辑器中搜索、对照原文。

### 二、表的通用结构

| 字段名 | 提取值 | 原文依据 | 章节位置 |
|--------|--------|----------|----------|
| 运营主体公司全称 | 深圳市腾讯计算机系统有限公司 | "运营主体为深圳市腾讯计算机系统有限公司" | 一、我们如何收集信息 |

但像"个人信息收集与使用"这种有十多个字段的模块，一张表排不下所有列。所以分两种表型：

### 三、两种表型

**A型 — 纵向表（适用于字段多、记录少的模块）**

一行一个字段，一组记录用空行或底色分隔。

| 提取记录 | 字段 | 提取值 | 原文依据 | 章节位置 |
|----------|------|--------|----------|----------|
| **记录1：注册登录** | 业务场景/功能 | 注册登录 | "当您注册账号时..." | 1.1 |
| | 收集的信息类别 | 手机号码 | "需要您提供手机号码" | 1.1 |
| | 信息具体字段 | 手机号 | "需要您提供手机号码" | 1.1 |
| | 信息来源 | 用户主动提供 | "您需要填写手机号" | 1.1 |
| | 使用目的 | 创建账号 | "用于创建账号" | 1.1 |
| | 处理必要性 | 功能所必需 | "为实现注册功能所必需" | 1.1 |
| | 是否敏感个人信息 | 否 | — | — |
| | 是否涉及未成年人 | 未说明 | — | — |
| | 原文依据汇总 | | "当您注册账号时，需要您提供手机号码用于创建账号..." | 1.1 |

每张 A 型表只处理一个提取记录，字段列到底，原文明确。

**B型 — 横向表（适用于记录多、字段少的模块）**

一行一个记录，列是字段名。适用于 SDK 清单、对外数据处理活动、Cookie 使用等模块。

| ID | SDK名称 | 提供方 | 使用目的 | 涉及字段 | 敏感权限 | 是否标识符 | 原文依据 | 章节 |
|----|---------|--------|----------|----------|----------|------------|----------|------|
| SDK-01 | 微信支付SDK | 财付通 | 支付 | 设备信息、订单信息 | 无 | OAID | "集成微信支付SDK，用于...收集设备信息" | 三、SDK清单 |
| SDK-02 | 高德地图SDK | 高德 | 定位导航 | 位置信息、设备信息 | 定位权限 | Android ID | "高德地图SDK将收集您的位置信息..." | 三、SDK清单 |

### 四、各模块的表型分配

这是整体提取计划的表结构：

| 模块 | 表型 | 说明 |
|------|------|------|
| **1. 章节结构** | B型 | 一行一个章节。列：标题级别、原始标题、标准化类别、章节概述、原文、位置 |
| **2. 产品范围与运营主体** | B型（运营主体表 + 产品范围表各一张） | 运营主体表：一行一个主体。产品范围表：一行一个产品 |
| **3. 个人信息收集与使用** | A型（每个场景一张表） | 字段多，纵向展开。按业务场景/功能分组 |
| **4. 营销与个性化推荐** | A型（每条活动一张表） | 字段多（12个），含关闭方式和影响 |
| **5. Cookie及同类技术** | A型（每种Cookie一张表） | 字段多（12个），含技术类型、必要/非必要 |
| **6. 对外数据处理活动** | B型（活动清单表） | 一行一个活动。另有一张总体原则表 |
| **7. SDK与第三方插件** | B型（SDK清单表） | 一行一个SDK，这是最标准的行列格式 |
| **8. 安全措施汇总** | B型 | 一行一个措施，带出现频率标记 |
| **9. 未成年人保护** | B型（按服务类别） | 一行一个服务类别，带原文依据 |

### 五、原文追溯的实现方式

**A型表**：每个字段行都有单独的"原文依据"列，字段值直接对应到原文句子。

例如：

| 提取记录 | 字段 | 提取值 | 原文依据 | 章节位置 |
|----------|------|--------|----------|----------|
| **记录1：注册登录** | 信息具体字段 | 手机号 | "需要您提供手机号码" | 一、1.1 |
| | 信息具体字段 | 昵称 | "以及昵称" | 一、1.1 |

字段值"手机号"的原文就是"手机号码"——提取的是同一个东西，但原文里写的是"手机号码"不是"手机号"，表中如实反映。

**B型表**："原文依据"列放在最右侧，保留该行主要字段所对应的原文句子。

### 六、跟纯 JSON 方案的关系

表格用于**人工阅读和复核**。如果后续需要程序处理，可以同时输出一份**精简 JSON**（不含原文，只含值和记录ID），通过 `记录ID` 与表格中的原文条目关联。

```
输出物清单（每份政策）：
  隐私政策_{产品名}_提取表.md     ← 可读的 Markdown 表格，供人工复核
  隐私政策_{产品名}_数据.json     ← 结构化 JSON（含 recordId，不含原文正文）
  隐私政策_{产品名}_原文索引.json ← 原文依据映射表（recordId → {字段名 → {原文, 章节位置}}）
```

这样三者可以交叉索引，程序处理走 JSON，人工核查翻表格。

---

### 七、几个关键细节

1. **"未说明"都带原文上下文**：填"未说明"时，原文依据列写"原文未提及相关内容"，而不是空着，确保 reviewer 能区分"没翻到"和"原文真的没有"
2. **原文依据尽量精确**：一句原文可能支撑多个字段，就重复引用。不嫌啰嗦，可追溯性优先
3. **章节位置统一**：用原文的一级/二级标题编号，不额外编一套
4. **一行一记录**：A 型表里，同属于一个提取记录的字段行，用 `提取记录` 列的值分组。这样你不会丢上下文
